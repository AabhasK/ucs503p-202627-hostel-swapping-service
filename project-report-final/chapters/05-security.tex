\chapter{Security and Integrity}
\label{ch:security}

The service decides who lives in which room, so the two things it must
protect are \emph{access} (only the right person can act for a student
or a hostel) and \emph{integrity} (the record of rooms cannot be
altered, and no student can be trapped by the workflow).

\section{Authentication}

The service uses no external identity provider. Authentication is built
from the Python standard library:

\begin{itemize}
  \item \textbf{Passwords} are stored as salted PBKDF2-HMAC-SHA256 hashes
  with 200\,000 iterations and a random 16-byte salt per password, in
  line with current guidance \cite{nist2017sp80063b}. Hashes are
  compared in constant time (\texttt{secrets.compare\_digest}).
  \item \textbf{Sign-in} accepts a roll number or an email. A wrong
  identifier and a wrong password give the same \texttt{401} answer, so
  the response does not reveal which accounts exist.
  \item \textbf{Sessions} are opaque random tokens stored server-side in
  the \texttt{sessions} table, with a seven-day lifetime. Unlike a
  self-contained token, a session can be revoked: logout deletes it.
  \item \textbf{The cookie} that carries the token is \texttt{httpOnly}
  (scripts cannot read it), \texttt{SameSite=Lax} (not sent on
  cross-site form posts) and, in production, \texttt{Secure} (sent only
  over HTTPS). It is not \texttt{Secure} in development, because local
  development runs over plain \texttt{http://localhost}.
  \item \textbf{A 30-second session cache} per process avoids reading the
  session row several times per page load. Logout clears the cached
  entry, so a logout still takes effect at once.
\end{itemize}

\section{Authorisation}

Every student and admin route depends on \texttt{require\_role}, which
answers \texttt{401} without a valid session and \texttt{403} for the
wrong role. Student routes act only on the signed-in student: the
student's identity comes from the session, never from the request body.
Offering a chain additionally checks that the student is a member of it,
and responding checks that the student is a member of the proposal.

\section{Integrity of the Record}

\begin{itemize}
  \item \textbf{Append-only allocations}: database triggers reject any
  \texttt{UPDATE} or \texttt{DELETE} on \texttt{allocations}, whatever
  client sends it.
  \item \textbf{One live proposal per student}: a partial unique index,
  so two chains can never claim the same student at the same time, even
  under concurrent offers.
  \item \textbf{No permanent lock-out}: proposals expire after three
  days, and members of settled proposals are freed
  (Section~\ref{sec:expiry-defect}).
  \item \textbf{Round rules}: priorities cannot change after a round is
  locked, and results are shown only once a round has completed.
\end{itemize}

\section{Fail-Fast in Production}
\label{sec:failfast}

Without a database the service serves the demo cohort. That is useful
in development, but in production it would show made-up students and
rooms to real students. With \texttt{APP\_ENV=production}, the service
refuses to start, and refuses to serve the demo endpoint, if
\texttt{DATABASE\_URL} is not set. Private keys and certificate files
(\texttt{*.pem}, \texttt{*.key}) and \texttt{.env} are ignored by Git,
so credentials do not reach the repository.
